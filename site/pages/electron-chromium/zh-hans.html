在 Electron 应用中伪造日期

搜索这个问题，所有的答案都是改你自己的代码——模拟 Date 对象、使用测试框架的假定时器。而当你手里是一个已经构建好的应用时，这些统统帮不上忙。这个工具运行的，就是你已有的那个应用。

为什么注入够不到它

这种模式的出现，源于一次具体的失败。一个基于 Electron 构建的番茄钟，在 x60 会话下运行时，倒计时纹丝不动。把应用的打包文件拆开来看，发现了两个相互独立的原因，而且在原生这一侧都无法修复：

  • 倒计时根本没有读取时钟。它是一个由 setInterval 递增的计数器，运行在 Web Worker 里。没有任何时间调用可以拦截，因为应用从来没有询问过现在几点。
  • 那个 worker 位于沙盒渲染进程中，而这恰恰是从外部注入的库进不去的地方。

所以，Windows 一侧的机制在这里帮不上忙，答案是改为与应用自己的 JavaScript 引擎对话。

改用什么办法

应用启动时带有一个调试端口和一个干净的一次性配置文件，它自己的时间 API 通过 DevTools 协议被放到会话时钟上——Date.now、new Date() 构造函数、performance.now、setTimeout 和 setInterval。

这一覆盖会安装到应用打开的每一个上下文中，包括它的 Web Worker——计时器往往就藏在那里，也是原生注入永远够不到的那个地方。

你的操作方式完全不变。同样的命令，同样的窗口，同样带有两个时钟和判定的会话面板。 

# 与原生应用相同的命令——模式会被自动识别
chrono run "%LOCALAPPDATA%\Programs\your-app\YourApp.exe" --at 2038-01-01T00:00:00 --mode x60

开始之前值得了解的两个限制

这种启动方式具有侵入性，并且有意对此毫不掩饰。

应用启动时会打开一个远程调试端口，并使用 %TEMP% 下一个全新的独立配置文件——它不会在你真实的配置文件上运行，也不是系统托盘里已经存在的那个副本。配置文件会在会话结束时删除；如果删除不了，会话摘要会如实说明，而不是悄悄把它留在那里。

如果你传入自己的 --user-data-dir 或 --remote-debugging-port，它们会被拒绝而不是被覆盖，因为那种显而易见的意外——让会话指向你真实的浏览器配置文件——不值得放任它发生。

会话时区跟随宿主机。

在这种模式下，时刻是伪造的，但本地时间的取值方法没有被伪造，所以独立的时区只是原生模式的功能。这是当前版本的局限，而不是有意的决定。

还有一件会让人意外的事：当你在会话中途改变速度时，已经排定的间隔计时器会保持原来的速率。Date.now、new Date() 和 performance.now 会立即响应，而正在运行的 setInterval 不会，会话会就此发出警告，而不是让你得出“这次改动什么都没做”的结论。

测试得如何

实验性，这个词在这里有明确的含义：它在当初开发时针对的目标上可以工作，尚未经过广泛测试，而内置的审计才是你的事实依据，而不是本页面。它是由人工验证的，而不是由自动化测试套件完成的，针对的是 64 位 Windows 上的一个真实 Electron 应用。

讓一個應用程式的時鐘走得更快

30 天的試用期要等 30 天才會到期，除非你能撥動時間。常見的建議是把系統時鐘往前撥，這需要系統管理員權限，還會把電腦上的其他所有程式一起拖走。這個工具改為只撥動一個處理序。

能快多少

選擇一個整數倍率。應用程式的時鐘會從工作階段開始的那個時刻起，以真實時鐘的這麼多倍速度前進。

倍率真實的一分鐘變成適用於
x60一小時每小時的工作、工作階段逾時、權杖壽命
x1440一天每日翻篇，半小時跑完 30 天試用期
x4320030 天的試用期趁你讀這段話的工夫，看著整個試用期結束
x525600一年年度續約、憑證到期
x1000000約 1.9 年上限
 
# 從目前的真實時間開始，每分鐘跑一天
chrono run "C:\apps\test.exe" --mode x1440

# 從選定的日期開始，並從那裡加速
chrono run "C:\apps\test.exe" --at 2027-12-01T09:00:00 --mode x1440

# 反過來，讓時鐘完全靜止
chrono run "C:\apps\test.exe" --mode frozen

容易讓人栽跟頭的地方：時鐘有兩個

加快掛鐘時間——也就是 DateTime.Now 及其同類回傳的值——本身並不會加快倒數。這是應用程式可以向作業系統提出的兩個不同的問題，而很多軟體是用後者而不是前者來衡量「三十天」的。

所以時長軸——計時刻度、睡眠、等待與計時器——是一個單獨的開關：

  • --scale-duration 把睡眠、等待與計時器也放到工作階段時鐘上。沒有它，x1440 會讓日曆飛速向前，而一個五秒的計時器仍然要花五個真實秒。
  • --scale-qpc 額外縮放高解析度計數器。Python 3.13+ 的 monotonic、.NET 的 Stopwatch 與 Java 的 nanoTime 都是從這裡讀取經過的時間，它預設關閉，因為在測試中縮放它會讓畫面轉譯不穩定。

如果倍率看起來對倒數毫無作用，幾乎總是這個原因。 

# 計時器應用程式：日曆與倒數一起加速
chrono run "C:\apps\Timer.exe" --mode x60 --scale-duration

# 用高解析度計數器量測經過時間的 Python 或 .NET 應用程式
chrono run "C:\apps\Job.exe" --mode x60 --scale-duration --scale-qpc

不重新啟動就改變速度

倍率可以在工作階段中途改變，時鐘是被重新錨定而不是跳變的，所以速度降低時它絕不會倒退。你也可以直接讓時鐘跳轉——往前，或是像筆電與時間伺服器重新同步後那樣往後，這正是會破壞任何沒有保護措施地量測經過時間的東西的情形。 

# 以 x60 執行，兩秒之後切換到 x1440
chrono run "C:\apps\test.exe" --mode x60 --set-after 2:1440

# 執行，五秒之後把時鐘跳到選定的時刻
chrono run "C:\apps\test.exe" --jump-after 5:2028-01-01T00:00:00

它不會做的事

  • 它不會動系統時鐘。這是重點，而不是限制——但這意味著任何從伺服器、資料庫或另一台電腦讀取時間的東西都不會受影響，出現這種情況時稽核會告訴你。
  • 跳轉改變的是應用程式看到的時間，而不是它何時被喚醒。已經交給核心的計時器依真實時間執行。大多數應用程式會輪詢時鐘，所以跳轉在實務上是有效的——但並非全部如此。
  • 它不會讓時間變慢。倍率是一及以上的整數，外加零倍率的凍結時鐘。

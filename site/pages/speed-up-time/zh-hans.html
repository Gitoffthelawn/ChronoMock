让一个应用的时钟走得更快

30 天的试用期要等 30 天才会到期，除非你能拨动时间。常见的建议是把系统时钟往前拨，这需要管理员权限，还会把机器上的其他所有程序一起拖走。这个工具改为只拨动一个进程。

能快多少

选择一个整数倍率。应用的时钟会从会话开始的那个时刻起，以真实时钟的这么多倍速度前进。

倍率真实的一分钟变成适用于
x60一小时每小时的任务、会话超时、令牌寿命
x1440一天每日翻篇，半小时跑完 30 天试用期
x4320030 天的试用期趁你读这段话的工夫，看着整个试用期结束
x525600一年年度续费、证书到期
x1000000约 1.9 年上限
 
# 从当前的真实时间开始，每分钟跑一天
chrono run "C:\apps\test.exe" --mode x1440

# 从选定的日期开始，并从那里加速
chrono run "C:\apps\test.exe" --at 2027-12-01T09:00:00 --mode x1440

# 反过来，让时钟完全静止
chrono run "C:\apps\test.exe" --mode frozen

容易让人栽跟头的地方：时钟有两个

加快挂钟时间——也就是 DateTime.Now 及其同类返回的值——本身并不会加快倒计时。这是应用可以向操作系统提出的两个不同的问题，而很多软件是用后者而不是前者来衡量“三十天”的。

所以时长轴——滴答计数、休眠、等待和定时器——是一个单独的开关：

  • --scale-duration 把休眠、等待和定时器也放到会话时钟上。没有它，x1440 会让日历飞速向前，而一个五秒的定时器仍然要花五个真实秒。
  • --scale-qpc 额外缩放高分辨率计数器。Python 3.13+ 的 monotonic、.NET 的 Stopwatch 和 Java 的 nanoTime 都是从这里读取经过的时间，它默认关闭，因为在测试中缩放它会让渲染不稳定。

如果倍率看起来对倒计时毫无作用，几乎总是这个原因。 

# 计时器应用：日历和倒计时一起加速
chrono run "C:\apps\Timer.exe" --mode x60 --scale-duration

# 用高分辨率计数器测量经过时间的 Python 或 .NET 应用
chrono run "C:\apps\Job.exe" --mode x60 --scale-duration --scale-qpc

不重启就改变速度

倍率可以在会话中途改变，时钟是被重新锚定而不是跳变的，所以速度降低时它绝不会倒退。你也可以直接让时钟跳转——向前，或者像笔记本与时间服务器重新同步后那样向后，这正是会破坏任何没有保护措施地测量经过时间的东西的情形。 

# 以 x60 运行，两秒之后切换到 x1440
chrono run "C:\apps\test.exe" --mode x60 --set-after 2:1440

# 运行，五秒之后把时钟跳到选定的时刻
chrono run "C:\apps\test.exe" --jump-after 5:2028-01-01T00:00:00

它不会做的事

  • 它不会动系统时钟。这是重点，而不是局限——但这意味着任何从服务器、数据库或另一台机器读取时间的东西都不会受影响，出现这种情况时审计会告诉你。
  • 跳转改变的是应用看到的时间，而不是它何时被唤醒。已经交给内核的定时器按真实时间运行。大多数应用会轮询时钟，所以跳转在实践中是有效的——但并非全部如此。
  • 它不会让时间变慢。倍率是一及以上的整数，外加零倍率的冻结时钟。
